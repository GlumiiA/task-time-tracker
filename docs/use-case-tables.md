# Таблицы прецедентов использования

Ниже собраны основные use case проекта `Task Time Tracker`. Эти сценарии используются как ориентир для тестов и проверки поведения системы.

## Сводная таблица

| UC | Прецедент | Краткое описание | Основные тесты |
| --- | --- | --- | --- |
| UC-01 | Авторизация пользователя | Пользователь входит в систему и получает JWT. | `AuthServiceTest`, `JwtProviderTest`, `SecurityFiltersTest`, `RestControllerMockitoIntegrationTest#loginReturnsAccessToken` |
| UC-02 | Получение списка своих задач | Сотрудник видит только назначенные ему задачи. Администратор может видеть все или отфильтрованные задачи. | `TaskServiceTest`, `RestControllerMockitoIntegrationTest#getTasksReturnsFilteredTasks` |
| UC-03 | Получение деталей задачи | Пользователь открывает карточку задачи по ID. | `TaskServiceTest`, `RestControllerMockitoIntegrationTest#getTaskByIdReturnsTask` |
| UC-04 | Создание задачи | Администратор создает новую задачу со статусом `NEW`. | `TaskServiceTest`, `RestControllerMockitoIntegrationTest#createTaskReturnsCreatedTask` |
| UC-05 | Обновление задачи | Администратор редактирует название и описание задачи. | `TaskServiceTest`, `RestControllerMockitoIntegrationTest#updateTaskReturnsUpdatedTask` |
| UC-06 | Назначение исполнителя | Администратор назначает сотрудника на задачу. | `TaskServiceTest`, `RestControllerMockitoIntegrationTest#updateStatusAndAssigneeDelegateToService` |
| UC-07 | Изменение статуса задачи | Исполнитель или администратор меняет статус задачи. | `TaskServiceTest`, `RestControllerMockitoIntegrationTest#updateStatusAndAssigneeDelegateToService` |
| UC-08 | Удаление задачи | Администратор удаляет задачу из системы. | `TaskServiceTest`, `RestControllerMockitoIntegrationTest#deleteTaskReturnsNoContent` |
| UC-09 | Создание time record | Сотрудник фиксирует рабочее время по задаче, если она в статусе `IN_PROGRESS` или `REVIEW`. | `TimeRecordServiceTest`, `TimeRecordMapperTests`, `RestControllerMockitoIntegrationTest#createTimeRecordReturnsCreatedRecord` |
| UC-10 | Просмотр своих time records | Сотрудник смотрит свои записи времени за период. | `TimeRecordServiceTest`, `RestControllerMockitoIntegrationTest#getTimeRecordsReturnsFilteredRecords` |
| UC-11 | Просмотр всех time records | Администратор может видеть все записи времени либо записи конкретного сотрудника. | `TimeRecordServiceTest`, `RestControllerMockitoIntegrationTest#getTimeRecordsReturnsFilteredRecords` |
| UC-12 | Получение суммарных часов сотрудника | Система считает общее количество часов сотрудника за период. | `TimeRecordServiceTest`, `RestControllerMockitoIntegrationTest#getTimeSummaryReturnsTotals` |
| UC-13 | Проверка ошибок и валидации | Система возвращает понятные ошибки для невалидных данных и нарушений прав доступа. | `ApiExceptionHandlerTest`, `TimeRecordServiceTest`, `TaskServiceTest`, `RestControllerMockitoIntegrationTest` |

## Подробности по use cases

### UC-01: Авторизация пользователя

| Поле | Значение |
| --- | --- |
| Название | Авторизация пользователя |
| Основные акторы | Гость, пользователь |
| Предусловия | Пользователь существует в системе и вводит корректные учетные данные. |
| Основной поток | 1. Пользователь отправляет логин и пароль.<br>2. Система проверяет учетные данные.<br>3. Система создает JWT для пользователя.<br>4. Система возвращает токен и сведения о пользователе. |
| Альтернативный поток | A1. Если логин или пароль неверны, система возвращает `401 Unauthorized`.<br>A2. Если данные запроса невалидны, система возвращает `400 Bad Request`. |
| Постусловия | Пользователь получает JWT и может выполнять защищенные запросы. |

### UC-02: Получение списка своих задач

| Поле | Значение |
| --- | --- |
| Название | Получение списка своих задач |
| Основные акторы | Сотрудник, администратор |
| Предусловия | Пользователь авторизован. |
| Основной поток | 1. Пользователь запрашивает список задач.<br>2. Система определяет роль пользователя и доступные фильтры.<br>3. Система выбирает задачи, доступные текущему пользователю.<br>4. Система возвращает список задач. |
| Альтернативный поток | A1. Если пользователь не авторизован, система возвращает `401 Unauthorized`.<br>A2. Если параметры фильтрации невалидны, система возвращает `400 Bad Request`. |
| Постусловия | Пользователь видит список задач, доступных ему по правам доступа. |

### UC-03: Получение деталей задачи

| Поле | Значение |
| --- | --- |
| Название | Получение деталей задачи |
| Основные акторы | Сотрудник, администратор |
| Предусловия | Пользователь авторизован, задача с указанным ID существует. |
| Основной поток | 1. Пользователь запрашивает задачу по ID.<br>2. Система проверяет права доступа.<br>3. Система находит задачу и связанные данные.<br>4. Система возвращает карточку задачи. |
| Альтернативный поток | A1. Если задача не найдена, система возвращает `404 Not Found`.<br>A2. Если у пользователя нет доступа к задаче, система возвращает `403 Forbidden`. |
| Постусловия | Пользователь получает подробную информацию о задаче. |

### UC-04: Создание задачи

| Поле | Значение |
| --- | --- |
| Название | Создание задачи |
| Основные акторы | Администратор |

| Основной поток | 1. Администратор заполняет данные новой задачи.<br>2. Система проверяет обязательные поля и валидность данных.<br>3. Система создает задачу со статусом `NEW`.<br>4. Система возвращает созданную задачу. |
| Альтернативный поток | A1. Если пользователь не является администратором, система возвращает `403 Forbidden`.<br>A2. Если данные задачи невалидны, система возвращает `400 Bad Request`. |

| Альтернативный поток | A1. Если задача не найдена, система возвращает `404 Not Found`.<br>A2. Если данные невалидны, система возвращает `400 Bad Request`.<br>A3. Если пользователь не администратор, система возвращает `403 Forbidden`. |

### UC-06: Назначение исполнителя

### UC-07: Изменение статуса задачи

| Поле | Значение |
| --- | --- |
| Название | Изменение статуса задачи |
| Основные акторы | Исполнитель, администратор |
| Предусловия | Пользователь авторизован, задача существует, пользователь имеет право менять статус. |
| Основной поток | 1. Пользователь отправляет новый статус задачи.<br>2. Система проверяет права доступа и допустимость перехода статуса.<br>3. Система обновляет статус задачи.<br>4. Система возвращает обновленную задачу. |
| Альтернативный поток | A1. Если статус недопустим, система возвращает `400 Bad Request`.<br>A2. Если у пользователя нет прав на изменение статуса, система возвращает `403 Forbidden`.<br>A3. Если задача не найдена, система возвращает `404 Not Found`. |
| Постусловия | Статус задачи изменен и сохранен. |

| Альтернативный поток | A1. Если задача не найдена, система возвращает `404 Not Found`.<br>A2. Если пользователь не администратор, система возвращает `403 Forbidden`. |

### UC-09: Создание time record

| Поле | Значение |
| --- | --- |
| Название | Создание time record |
| Основные акторы | Сотрудник, администратор |
| Предусловия | Пользователь авторизован, задача существует и находится в статусе `IN_PROGRESS` или `REVIEW`. |
| Основной поток | 1. Пользователь заполняет время начала и окончания работы.<br>2. Система проверяет права доступа и валидность интервала.<br>3. Система сохраняет запись времени.<br>4. Система возвращает созданную запись. |
| Альтернативный поток | A1. Если задача не в `IN_PROGRESS` или `REVIEW`, система возвращает `409 Conflict`.<br>A2. Если пользователь пытается создать запись за другого сотрудника, система возвращает `403 Forbidden`.<br>A3. Если интервал времени невалиден, система возвращает `400 Bad Request`. |
| Постусловия | Запись времени сохранена в системе. |

### UC-12: Получение суммарных часов сотрудника

| Поле | Значение |
| --- | --- |
| Название | Получение суммарных часов сотрудника |
| Основные акторы | Сотрудник, администратор |

| Основной поток | 1. Пользователь запрашивает summary по сотруднику и периоду.<br>2. Система проверяет права доступа.<br>3. Система находит time records за указанный период.<br>4. Система суммирует длительность всех записей.<br>5. Система возвращает итоговое число часов. |

### UC-13: Проверка ошибок и валидации

| Поле | Значение |
| --- | --- |
| Название | Проверка ошибок и валидации |
| Основные акторы | Пользователь, администратор |
| Предусловия | Пользователь отправляет запрос, который может содержать ошибки в данных или правах доступа. |
| Основной поток | 1. Пользователь отправляет запрос в систему.<br>2. Система валидирует входные данные и права доступа.<br>3. Система определяет тип ошибки, если она есть.<br>4. Система возвращает понятный HTTP-ответ с сообщением об ошибке. |
| Альтернативный поток | A1. Если данные невалидны, система возвращает `400 Bad Request`.<br>A2. Если доступ запрещен, система возвращает `403 Forbidden`.<br>A3. Если ресурс не найден, система возвращает `404 Not Found`.<br>A4. Если бизнес-правило нарушено, система возвращает `409 Conflict`. |
| Постусловия | Пользователь получает диагностическое сообщение, а система не изменяет данные при ошибке. |
